# WEB-01 publish contract — not an installed workflow

`webhook.json` is deliberately disabled and has no credential. Remove NOTE before using the provider API; configure it through Manage for the first test. It is not submitted by the prototype.

The candidate uses Sanity's native Publish, then a provider-managed webhook. Add an expiring **fine-grained GitHub PAT**, restricted to the isolated test repository with Contents:write, as the webhook's Authorization header in Sanity Manage. Never paste it in Studio config, source control, CI output, screenshots or chat. This grants Sanity custody of a privileged credential; rotate/revoke it and restrict project membership. A GitHub App token broker has a shorter credential lifetime but adds a service. Decide after the isolated test.

The webhook sends only the published ID/revision. It excludes draft and release-version events. The static build uses unauthenticated published-only reads. `requestBuild` is a mockable server-side equivalent for contract tests, not the live delivery implementation.

Future receiver workflow contract (WEB-09):

1. Live on the verified default branch of a separate test destination first. Subscribe only to `repository_dispatch: types: [sanity-published]`. Do not interpolate untrusted event fields into shell commands; use environment variables plus schema validation. No user-supplied repository/ref/command is accepted.
2. Check out a fixed reviewed source ref; use standard Ubuntu runners, `npm ci`, static build. Set `WEB01_CONTENT_SOURCE=sanity`, `WEB01_PROJECT_ID`, `WEB01_DATASET=web01`, `WEB01_EXPECTED_ID` and `WEB01_EXPECTED_REV`. Reject an obsolete requested revision; never silently render a newer one under an older revision's success record. Retry the latest publish after rejection.
3. Capture the complete published snapshot once and build exclusively from it. The current spike fetches per route and is **not an atomic multi-article production snapshot**. Before real deployment WEB-09 must materialize once, then feed that snapshot to every page/manifest. Check uniqueness and all required fields; don't render arbitrary HTML/JS from content.
4. Use one concurrency group for the entire snapshot/build/deploy job, with cancel-in-progress false; no independent per-article deploys. Recheck source state before deploying. GitHub queue order is not guaranteed: delayed requests must rebuild current state or be rejected. Prove the ordering behavior with rapid publications and unpublish. A state change between the final check and deploy remains a race; a durable generation/coordination mechanism may be needed if tests cannot establish the acceptance guarantee. This is unresolved, not claimed solved by concurrency alone.
5. Upload **only** the static `dist/`, never Studio sources, exports, environment files or private snapshots. Deployment job alone receives `pages:write` and `id-token:write`; build job needs `contents:read`. Use the built-in per-job GITHUB_TOKEN for deployment, not the webhook PAT.
6. Include the same publication manifest in the artifact. Show requested → queued → building → live/failed in a small Studio status extension. Match run ID/revision, and fetch the live `publication.json` to confirm the desired revision before showing live. A 204 dispatch response means requested, not queued or live. Use a GitHub Actions link as an interim manual check; do not call this complete editor feedback. Handle rate limits, timeouts, canceled/superseded runs, token expiry and offline state explicitly.
7. Retry can send duplicate events; use ID/revision for correlation and a stable slug for replacement. Never create a new CMS document on retry. Duplicate run suppression and actual failure recovery still need live testing.

Unpublish is intentionally excluded from the prototype webhook. WEB-09 must add a delete trigger using `before()` fields and a desired-state rebuild, remove stale output/routes/sitemap entries, and test that retries cannot resurrect an article. No deployable workflow is shipped here, to prevent accidental production execution.
